Архитектура приложения
======================

Общая структура
---------------

Приложение реализовано по многослойной архитектуре (Layered Architecture)
с элементами MVC. Каждый слой решает одну задачу и зависит только от слоя
«под собой».

.. code-block:: text

    ┌──────────────────────────────────────────────────────────────┐
    │  Уровень представления — app/ui.py                          │
    │  MainWindow, QueueList, Preview, RoundedButton, CheckBox,   │
    │  QualitySlider, ProgressBar                                │
    └───────────────┬──────────────────────────────┬───────────────┘
                    │ Preset, QueueItem            │ callback-функции
    ┌───────────────▼──────────────┐   ┌───────────▼───────────────┐
    │  Уровень бизнес-логики      │   │  Фоновый поток             │
    │  app/processor.py           │   │  app/worker.py             │
    │  ImageProcessor             │   │  ProcessingWorker          │
    └───────────────┬──────────────┘   └───────────┬───────────────┘
                    │                                  │
    ┌───────────────▼──────────────────────────────────▼───────────────┐
    │  Уровень доступа к данным — app/database.py                     │
    │  DatabaseManager, default_data_dir                              │
    └───────────────────────────────────┬──────────────────────────────┘
                                        │
    ┌───────────────────────────────────▼──────────────────────────────┐
    │  Модели данных — app/models.py: Preset, QueueItem               │
    │  Хранилище: SQLite, файл data/presets.db                         │
    └──────────────────────────────────────────────────────────────────┘

Используемые паттерны проектирования
------------------------------------

Model-View-Controller
~~~~~~~~~~~~~~~~~~~~~

* **Model** — :class:`app.models.Preset` и :class:`app.models.QueueItem`,
  а также слой доступа к данным :class:`app.database.DatabaseManager`.
* **View** — класс :class:`app.ui.MainWindow` и набор вспомогательных
  виджетов на ``Canvas``: ``RoundedButton``, ``CheckBox``, ``QualitySlider``,
  ``ProgressBar``, ``QueueList``, ``Preview``.
* **Controller** — класс :class:`app.worker.ProcessingWorker`, который
  запускает обработку и сообщает интерфейсу о ходе работы.

Repository
~~~~~~~~~~

Класс ``DatabaseManager`` скрывает особенности SQL: остальные модули
работают с методами ``create_preset``, ``get_preset``, ``log_processed_file``
и не знают структуры таблиц.

Observer / Callback
~~~~~~~~~~~~~~~~~~~

Обработчик не знает о Tkinter, а окно не знает о деталях обработки. Связь
между ними обеспечивают функции обратной связи ``on_update``, ``on_progress``
и ``on_finish``. События передаются через потокобезопасную очередь
``queue.Queue`` и обрабатываются в главном потоке интерфейса.

Инкапсуляция состояния
~~~~~~~~~~~~~~~~~~~~~~

Модели объявлены через ``dataclass``, поэтому значения по умолчанию заданы
в одном месте, а создание объекта проверяется типами.

Singleton
~~~~~~~~~

Единственного экземпляра базы нет намеренно: окно создаёт один
``DatabaseManager`` и живёт вместе с ним, что упрощает тестирование —
в тестах подставляется база во временной папке.

Взаимодействие слоёв
--------------------

Сценарий «пользователь нажал кнопку СТАРТ»:

1. ``MainWindow.start_processing`` собирает значения полей формы
   в объект ``Preset`` и проверяет их методом ``_validate_preset``.
2. Профиль сохраняется в базе, создаётся запись сессии
   ``DatabaseManager.create_session``.
3. Создаётся ``ProcessingWorker``, которому передаются очередь, пресет,
   обработчик и три функции обратной связи.
4. Рабочий поток последовательно вызывает
   :meth:`app.processor.ImageProcessor.process` для каждого файла и
   публикует события в очередь.
5. Главный поток окна опрашивает очередь по таймеру, обновляет карточки
   очереди, индикатор прогресса и блок сравнения «до и после».
6. После завершения результаты сессии записываются в журнал.

Именно такое разделение позволяет писать системные тесты: окно поднимается
реально, а обработка и база подменяются на время выполнения теста.

Схема базы данных
-----------------

Нормализация выполнена до третьей нормальной формы: справочник форматов
вынесен в отдельную таблицу, настройки водяного знака — в дочернюю.

.. code-block:: text

    tbl_formats (1) ─────< tbl_presets (1) ─────< tbl_watermarks
                            │                       ON DELETE CASCADE
                            │
                            └──< tbl_history_sessions >──< tbl_processed_files
                                    ON DELETE SET NULL    ON DELETE CASCADE

============================  =================================================
Таблица                       Содержимое
``tbl_formats``               Справочник из девяти целевых форматов
``tbl_presets``               Профили настроек обработки
``tbl_watermarks``            Текст, прозрачность и положение водяного знака
``tbl_history_sessions``      Журнал запусков: время, итоги, длительность
``tbl_processed_files``       Журнал по каждому файлу внутри сессии
============================  =================================================

Потокобезопасность
------------------

Обработка выполняется в отдельном потоке, поэтому:

* файловые операции и Pillow не блокируют интерфейс;
* отмена реализована через ``threading.Event`` и проверяется перед каждым файлом;
* обновление виджетов выполняется только в главном потоке — фоновый поток
  лишь кладёт события в очередь, которую опрашивает окно;
* поток создан как ``daemon``, поэтому не удерживает программу при закрытии.
